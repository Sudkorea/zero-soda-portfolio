# 데이터 흐름과 공개 예제

## 전체 제품에서 이 예제가 차지하는 위치

| 단계 | 기존 구현 | 역할 |
|---|---|---|
| 수집 | `cli.collect_live`, `danawa`, `community.collect_recent_config`, `retail` | 가격비교·개인 핫딜 기반 후보·편의점 행사 어댑터에서 후보 수집 |
| 보존·정리 | `cli.validate_discoveries`, `state.record_scan`, `core.build_offer` | 수집 후보와 거절 이유를 보존하고 음료 구성·용량·수량·가격 정리 |
| 검증 | `price_evidence`, 상품 식별 판정, 검증 작업/결과 | 가격 근거, 정확한 상품·판매 옵션, 일반 공개 조건 검사 |
| 가격 비교 | `app_read_model._candidate`, `build_app_read_model` | 배송비 포함 최종가를 수령 용량으로 나누고 상품·모드·용량별 순위 생성 |
| 앱 제공 | `static_data`, `miniapp/src/api.ts` | 앱용 정적 JSON으로 내보내고 클라이언트가 가격판·상세 데이터를 읽음 |

모듈명은 비공개 원본 프로젝트를 기준으로 합니다. 공개본에서는 아래의 가격 검증 경로만 실행할 수 있습니다.

`core.build_offer`는 전달받은 최종가로 원/L를 계산합니다. 배송비와 가격 근거는 어댑터와 후속 공개 기준에서 확인합니다. 편의점 어댑터는 지불 수량과 수령 수량을 구분합니다. Hotdeal Agent의 자연어 피드백 처리에는 LLM을 사용하지만, 이번에 공개한 가격 검증 예제에는 LLM이 없습니다.

## 실행 경로

```text
합성 판매처 표
  → parse_price_compare_sellers: 완전한 행과 불완전한 행을 함께 유지
  → _seller_table_settlement: 표 전체의 가격 충돌과 미확인 가격 하한 판정
  → demo.evaluate: 합성 목적지와 행별 증거 연결
  → price_comparison_row_is_publishable: 증거와 금액의 일치 여부 검사
  → gate_eligible 출력
```

원본에서는 `fetch_comparison_offers`가 목적지 해석과 행별 증거 연결을 수행합니다. 공개 예제는 네트워크 호출 대신 `shop.example.test`의 합성 URL을 사용합니다. 원본의 `state.record_scan`과 `app_read_model._complete_aggregator_evidence`는 같은 공통 가격 증거 함수를 호출합니다.

## 비교 전제와 판단 기준

이 단계에는 **동일한 상품·용량·수량의 판매처 표**가 전달된다고 전제합니다. 상품 동일성, 개인별 혜택과 정보의 현재 유효성은 이 예제가 별도로 보장하지 않습니다.

- **완전한 행:** 양수 상품가, 확인된 0원 이상의 배송비, 보고 합계와 상품가+배송비의 일치. 보고 합계가 `0` 또는 누락이면 미제공 값으로 보고 합계를 계산하는 원본 동작을 유지합니다.
- **완전한 표:** 가격 충돌이 없고 행별 증거가 맞으면 여러 행이 통과합니다. 이 함수가 1위 하나를 고르는 것은 아닙니다.
- **불완전한 표:** 확인된 최저 합계보다 다른 미확인 행의 상품가 하한이 모두 높을 때, 그 최저 합계의 완전한 행을 통과시킵니다. 하한도 알 수 없는 행이 있으면 보류합니다.
- **조건부 배송:** `deliveryPrice=16777215`, `differentialPostYN='Y'`, 양수 상품가와 동일한 `priceOrder`라는 원본의 정확한 조건일 때만 일반 공개가 경쟁에서 분리합니다. 무료 배송비가 아니라 해당 소스의 표식입니다. 조건부 행은 보존하고 다른 미확인 행·가격 충돌은 계속 검사합니다.
- **공통 검사:** 출처 종류, 목적지 문자열 일치, 판매처명 존재, 증거의 금액과 전달 금액 일치, 산술 정합성을 확인합니다.

## 미확인 후보와 동률일 때의 정책과 한계

현재 구현의 조건은 다음과 같습니다.

```text
모든 미확인 경쟁 행의 상품가 하한 > 확인된 최저 합계
```

B의 상품가가 15,000원이고 배송비가 음수가 아니라면, 총액은 15,000원 이상입니다. A의 확인된 총액이 15,000원이라면 A가 최저가 중 하나라는 판단은 가능합니다. 따라서 금액 비교만을 목적으로 할 때 엄격한 `>`는 필요한 조건보다 보수적입니다.

현재 정책은 **미확인 후보와의 동률 가능성도 보류**합니다. 반면 표의 배송비가 모두 확인되면 동률인 완전한 행들은 통과할 수 있습니다. 모든 동률을 금지하는 것은 아닙니다. 이 문서는 관찰되는 동작과 그에 따른 제한을 설명하며, 당시 이 조건을 선택한 동기를 새로 추정하지 않습니다.

공동 최저가를 허용하려면 같은 전제에서 `≥`도 검토할 수 있습니다. 단, 배송비 외의 미확인 할인 등이 상품가 하한을 무효화하지 않는지와 후속 순위·표시 정책을 함께 확인해야 합니다. 이번 공개 문서 편집에서는 원본 조건이나 테스트를 변경하지 않았습니다.

## 실행 결과의 범위

`gate_eligible`은 이 가격 검사 단계를 통과한 판매처입니다. 상품·옵션 일치, 쿠폰·회원 조건, 재고, 만료·최신성, 원/L 순위, 저장·재시도·앱 게시까지 완료됐다는 뜻은 아닙니다.

입력은 신뢰된 내부 증거 객체라는 원본 전제를 유지합니다. HTTPS 접두부와 문자열 일치는 확인하지만 URL 소유권·접속 성공을 인증하지 않습니다. 임의 외부 JSON을 위한 완전한 스키마 검증기도 아니며, 원본의 `int()` 변환·타입 가정을 그대로 사용합니다.

합성 입력의 회귀 검사는 이 경로의 동작 확인이며, 실제 상품 데이터 정확도나 LLM 성능 평가가 아닙니다.
