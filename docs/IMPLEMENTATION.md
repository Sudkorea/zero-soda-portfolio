# 가격 검증: 입력에서 출력까지

[제품 소개](../README.md) · [테스트와 기대 결과](VERIFICATION.md)

## 전체 제품에서의 위치

제품은 가격과 행사를 수집한 뒤 상품·구매 조건을 정리하고, 검증을 거친 후보의 리터당 가격을 계산해 앱에 제공합니다. 여기서는 그중 **한 상품의 판매처 표에 배송비가 빠진 행이 있을 때, 어떤 가격을 비교 후보로 쓸 수 있는지** 다룹니다.

공개 예제는 실제 판매처에 접속하지 않습니다. 기존 파싱·판정 함수를 사용하되, 네트워크 연결은 합성 URL로 대체했습니다. 전체 앱이 아니라 이 처리 경로만 실행할 수 있습니다.

## 입력과 전제

입력은 [scenarios.json](../examples/scenarios.json)의 합성 판매처 표입니다. 각 판매처 행에는 상품가(`mobilePrice` 또는 `minPrice`), 배송비(`deliveryPrice`), 보고 합계(`priceOrder`), 판매처·상품 식별 정보가 들어갑니다.

**상품·용량·수량이 같은 판매처 표**라는 전제에서 총액을 비교합니다. 배송비는 0원 이상이고 별도 할인으로 상품가가 낮아지지 않아야, 상품가를 최종 결제금액의 하한으로 사용할 수 있습니다. 상품 동일성 확인과 개인별 쿠폰·회원 혜택 처리는 이 예제 밖의 일입니다.

## 코드는 어떤 질문에 답하나?

| 순서 | 확인하는 질문 | 코드 |
|---|---|---|
| 1. 가격 정리 | 상품가와 배송비로 총액을 계산할 수 있는가? | [seller_table.py](../examples/seller_table.py)의 `_seller_price`, `parse_price_compare_sellers` |
| 2. 표 전체 판정 | 미확인 행이 더 저렴할 가능성이나 가격 충돌이 남아 있는가? | 같은 파일의 `_seller_table_settlement` |
| 3. 행별 검사 | 표의 판단 근거와 전달할 가격·목적지가 일치하는가? | [price_evidence.py](../examples/price_evidence.py)의 `price_comparison_row_is_publishable` |
| 4. 예제 실행 | 합성 데이터를 연결하면 어떤 후보가 통과하는가? | [demo.py](../examples/demo.py)의 `evaluate` |

### 1. 계산할 수 없는 행도 남겨 둡니다

양수 상품가와 0원 이상의 배송비가 있고, 보고 합계가 상품가+배송비와 맞으면 계산 가능한 행으로 표시합니다. 보고 합계가 `0` 또는 누락이면 합계가 제공되지 않은 것으로 보고 직접 계산합니다.

배송비가 없거나 금액이 맞지 않는 행에는 실패 이유를 붙여 판정 목록에 남깁니다. 완전히 같은 판매처 행은 중복 제거합니다. 이때의 ‘보존’은 **판정 과정에서 행을 버리지 않는 것**이며, 공개 예제에 DB 저장 기능은 없습니다.

### 2. 미확인 행의 가격 하한과 충돌을 봅니다

가격을 계산할 수 있는 행들에서 최저 총액을 구하고, 미확인 경쟁 행의 상품가와 비교합니다. 하한을 알 수 없거나 그 하한이 최저 총액 이하이면 후보 선정을 보류합니다. 같은 판매처·옵션으로 묶인 완전한 행들의 가격 구성이 다를 때도 표의 가격 충돌로 처리합니다.

```text
표에 가격 충돌이 있음 → 통과 후보 없음
가격이 모두 확인됨 → 행별 검사를 통과한 후보들을 반환
미확인 행이 있음
    ├─ 모든 미확인 경쟁 행의 하한 > 확인된 최저 총액
    │     → 그 최저 총액의 완전한 행만 다음 검사로 전달
    └─ 하한 불명 또는 최저 총액 이하 → 통과 후보 없음
```

#### 수집원별 조건부 배송 처리

원본 어댑터에는 `deliveryPrice=16777215`, `differentialPostYN='Y'`, 양수 상품가와 같은 `priceOrder`라는 조합을 조건부 배송 행으로 취급하는 규칙이 있습니다. 해당 행은 목록에 남지만 일반 구매 조건의 가격 경쟁에서는 분리됩니다. 다른 미확인 행과 가격 충돌은 계속 검사합니다.

이 값은 실제 배송비나 무료배송으로 계산하지 않습니다. 이 소스에 한정된 규칙이며, 공개 예제에는 판매처의 공식 필드 규격이 포함돼 있지 않습니다.

<a id="ties"></a>
### 동률 처리와 한계

**현재 코드의 규칙은 `>`입니다.** 미확인 B의 상품가가 15,000원이면, A의 확인된 총액 15,000원은 보류됩니다. 반면 B의 배송비가 0원으로 확인되면 두 행이 모두 통과할 수 있습니다. 모든 동률을 금지하는 것이 아니라, 미확인 후보와 동률일 가능성을 보류하는 동작입니다.

금액 비교만 보면 A도 최저가 중 하나라고 판단할 수 있으므로, 이 규칙은 필요 이상으로 후보를 줄일 수 있습니다. 공동 최저가를 허용하려면 같은 전제에서 `≥`를 검토할 수 있습니다. 적용할 때는 미확인 할인이 상품가 하한을 깨지 않는지와 후속 순위·표시 방식을 함께 확인해야 합니다.

### 3. 가격과 판단 근거가 일치하는지 검사합니다

행별 검사는 출처 종류, 판매처명, 목적지 문자열, 표의 판정 상태와 금액을 확인합니다. 근거 객체에 기록된 상품가·배송비·총액이 전달된 값과 같고, 상품가+배송비=총액이어야 통과합니다.

공개 예제는 **같은 파싱 결과로 가격과 근거 객체를 연결**합니다. 별도 판매처 조회와의 교차검증이 아니라, 앞 단계의 판단 근거와 뒤에 전달할 데이터의 일치를 검사하는 것입니다. 목적지는 합성 URL이며, HTTPS 접두부와 문자열 일치는 실제 접속 성공이나 상품 인증을 뜻하지 않습니다.

## 출력 읽기

[expected.json](../examples/expected.json)에서 시나리오별 기대 결과를 볼 수 있습니다.

| 필드 | 의미 |
|---|---|
| `rows_preserved` | 파싱·중복 제거 후 판정에 남은 행 수 |
| `complete_rows` | 가격을 계산할 수 있는 행 수 |
| `winner_settled` | 표 수준에서 가격 충돌과 미확인 가격 하한 조건을 통과했는지 |
| `gate_eligible` | 행별 가격 검사까지 통과한 판매처 목록 |

`gate_eligible`은 최종 1위 상품이 아닙니다. 표의 가격이 모두 확인되면 여러 판매처가 통과할 수 있고, 일부만 확인됐다면 위의 하한 조건을 만족하는 최저 총액의 행만 통과합니다. 각 행의 근거와 금액도 맞아야 합니다.

## 이 예제 밖에서 확인할 것

상품·옵션 일치, 재고, 가격의 최신성, 개인별 혜택은 별도 검증이 필요합니다. 원/L 순위 계산, 저장·재시도, 앱 게시도 이 예제에 포함되지 않습니다.

함수는 내부 처리 단계에서 정리된 증거 객체를 받는다는 전제이며, 원본의 `int()` 변환과 타입 가정을 유지합니다. 임의의 외부 JSON을 받는 완전한 입력 검증기로 사용하기 위한 코드는 아닙니다. 공개 경로에는 LLM 호출이 없습니다.
